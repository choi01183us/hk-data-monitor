# 部署

SPEC 第 3 節:**Cloudflare Pages 或 GitHub Pages,二揀一,唔好兩邊都整。**

已揀 **GitHub Pages**。理由:每週重抓數據本身就一定要用 GitHub Actions,
用 GitHub Pages 就成個流程留喺同一個平台 —— 唔使開多個戶口、唔使管 API token secret、
一個 workflow 由抓數到上線做曬。SPEC 第 1 節話任何令維護成本上升嘅設計都要拒絕。

## 一次性設定

本專案已於2026-09-10完成首次 GitHub Pages 發布：
[正式網站](https://choi01183us.github.io/hk-data-monitor/) ·
[儲存庫](https://github.com/choi01183us/hk-data-monitor) ·
[Actions 紀錄](https://github.com/choi01183us/hk-data-monitor/actions)。
目前 Pages 使用 `workflow` 建置模式並強制 HTTPS；已有 `origin` 的本機副本毋須重做以下設定。
真機及課堂試用仍按文末清單另行實測。

### 1. 推上 GitHub

```bash
# repo 已經 git init 咗,而家喺本機
git remote add origin https://github.com/<你嘅帳戶>/hk-data-monitor.git
git branch -M main
git push -u origin main
```

### 2. 開 Pages

GitHub repo → **Settings** → **Pages** → **Source** 揀 **GitHub Actions**(唔係 "Deploy from a branch")。

> ⚠️ **一定要揀 GitHub Actions,唔好揀分支發佈。**
> 分支發佈會行 Jekyll,而 Jekyll 會靜靜哋掉走所有底線開頭嘅目錄 ——
> Framework 出嘅 `_observablehq/`、`_npm/`、`_file/`、`_import/` 全部都係,
> 即係成個站會冇晒,只剩返 HTML 骨架。
>
> 行 Actions 呢條路根本唔會經 Jekyll,所以亦都**唔使** `.nojekyll`。
> (就算你放個 `.nojekyll` 落 `dist/` 都上唔到去 —— `upload-pages-artifact` 預設排除所有 dotfile。)

### 3. 確認 workflow 有寫入權限

可以保留 repository 的唯讀預設。三份 workflow 已明確聲明所需權限：
刷新需要 `contents: write` 提交數據；部署需要 `pages: write` 及 `id-token: write`。
一般 repository 預設唔係不可提升的上限；實際權限亦可能受機構政策或事件類型限制。
遇到 403 先對照失敗步驟及該 job 的權限，唔好一律將整個 repo 的預設提升。
見 [GitHub workflow 權限計算](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#how-permissions-are-calculated-for-a-workflow-job)。

**本機首次推送係另一種權限。** 如果用 GitHub CLI 的 OAuth HTTPS 憑證，
新增 `.github/workflows/` 檔案需要 `workflow` scope；`repo` scope 本身唔足夠。
可用 `gh auth refresh -h github.com -s workflow`，由擁有人在 GitHub 完成裝置授權；
唔把密碼或 token 寫入 repo、遙距URL或對話。這項與 Actions 執行時的 `GITHUB_TOKEN` 分開。

### 4. 第一次部署

推上去之後 `deploy.yml` 會自動行。或者去 **Actions** → **部署去 GitHub Pages** → **Run workflow**。

先開啟 Pages，再執行建置。現有 `configure-pages` 只讀設定，不會替新 repo 自動開 Pages；
如首次 push 的 run 早於 Pages 設定，設定妥當後再重跑該次 run。

網址:`https://<你嘅帳戶>.github.io/hk-data-monitor/`

## 自訂網域

1. Settings → Pages → **Custom domain** 填你個網域,撳 Save
2. 去你個 DNS 供應商加紀錄:
   - 頂級網域(`example.com`):四條 `A` 紀錄指去 `185.199.108.153`、`185.199.109.153`、`185.199.110.153`、`185.199.111.153`
   - 子網域(`data.example.com`):一條 `CNAME` 指去 `<你嘅帳戶>.github.io`
3. DNS 生效之後,回 Settings → Pages 剔 **Enforce HTTPS**

改咗自訂網域**唔使改任何程式碼**:`actions/configure-pages` 會出一個空嘅 `base_path`,
`deploy.yml` 補條斜線變成 `/`,Framework 自動用返根路徑。

> Framework 出嘅連結本身全部係相對路徑,所以子路徑同根網域其實只有 `404.html` 有分別。

## 每週自動更新

`refresh-data.yml`,每星期一 **06:17(香港時間)**。

- 抓完 → 驗 schema → 跑檢查器自證 → 有變動先 commit → **喺同一個 run 重新部署**
- 單個來源抓唔到:保留上一版,網站照出,嗰版顯示「上一次成功更新嗰時嘅版本」提示
- 全部抓唔到:build 照樣成功(用晒舊數據),Actions summary 標紅
- `manual/` 永遠唔碰

手動觸發:Actions → **每週重抓數據** → Run workflow。
(有個 `deploy` 選項,揀 `false` 就淨係抓數唔部署,適合試嘢。)

### 兩件要留意嘅事

**排程有機會遲到甚至跳過。** GitHub 明講排喺高峰嘅 job 會延遲,負載大嗰陣會靜靜哋掉咗。
漏咗一個星期唔算 bug —— 下星期會補返。

**公開 repo 冇活動 60 日,排程會自動停。**
而「冇活動」點計 GitHub 冇明確定義,而且我哋個 workflow 數據冇變就唔會 commit ——
即係「跑咗但冇 commit」有機會唔算活動。放暑假前後留意下 Actions 版面有冇綠點。
停咗嘅話,去 Actions 撳 **Enable workflow** 就得。

## 本機驗離線

`npm run dev` 服務嘅係 `src/` 而且行喺根路徑,兩樣都同真實部署唔同。
Service worker 嘅 scope 同 precache 清單一定要喺「子路徑 + 真 `dist/`」條件下先驗得準:

```bash
npm run build
node tools/serve-dist.mjs        # http://localhost:8787/hk-data-monitor/
```

開個瀏覽器入去，保持連線讓 service worker 快取頁面同圖表 library；
唔用固定等候秒數當成功證據。可先在 DevTools 確認 worker 已控制頁面，
再到 Network 剔 **Offline**，reload 並打開一頁未曾瀏覽的指標。

應該見到:頁面照樣出、圖照樣畫、頁頂有一條「目前為離線快取,數據截至 YYYY 年 M 月 D 日」。

## 如果日後要轉去 Cloudflare Pages

SPEC 話二揀一,所以轉就要**停埋** GitHub Pages,唔好兩邊同時行。

要留意嘅分別:

- 用 `cloudflare/wrangler-action@v4`(`cloudflare/pages-action` 已經封存,唔好用)
- Cloudflare 支援 `_headers`,可以畀帶雜湊嘅資源設 immutable 快取;GitHub Pages 完全唔支援,
  焗死 `max-age=600`
- `dist/` 一定要有 `404.html`,否則 Cloudflare 會自動當 SPA,對任何唔存在嘅路徑回 `index.html` 同 HTTP 200
  (soft-404)。本專案有 `src/404.md`,所以冇呢個問題
- 尾斜線行為唔同:GitHub Pages 對 `/page/` 回 404,Cloudflare 會 308 轉去 `/page`
